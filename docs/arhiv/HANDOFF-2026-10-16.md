# DEEIX-RU — передача в Code: зависание VPS после отправки двух PDF (2026-10-16)

Читать вместе с `STATE.md` и `claude/SCAN-PDF.md`. Правила работы с пользователем: команды для VPS давать короткими блоками, тестовые скрипты начинать с `clear`, временные файлы и клоны после себя удалять, секреты и пароли не просить и не записывать.

## Задача
Выяснить, почему VPS (tap.teamdream.online) перестал отвечать (502 на сайте, не отвечал и 1Panel) после отправки в чат двух PDF, и сделать так, чтобы это не повторялось. Заодно проверить, не виноват ли патч `scan-pdf.patch`.

## Что известно (факты)
- Все времена в логах сервера по UTC (Москва = UTC+3).
- Сервер: ~709 МБ ОЗУ, на момент зависания swap не было. Свободно было ~295 МБ при работающем приложении.
- 15.10 в 21:17 UTC на VPS положен новый бэкенд-бинарник `/opt/deeix-ru/deeix-chat` (74 280 400 байт). В нём есть строка `pdf_scan_direct`, то есть патч для PDF-сканов в бинарнике был.
- Около 21:46 UTC пользователь загрузил два PDF: договор-скан (5,3 МБ) и доп. соглашение (978 КБ). В 21:47:33 UTC создан диалог и началась отправка. После 21:47:33 в логах приложения тишина, записи о завершении отправки сообщения нет.
- С 21:48:10 UTC до самой перезагрузки (21:59:28) в журнале каждые 15–30 с: `systemd-journald: Under memory pressure, flushing caches`. Записей об OOM-kill в тот период нет (последний OOM был 4 октября, убит `next-build` при сборке фронтенда). Вывод: система не упала, а «задохнулась» от нехватки памяти без swap.
- Пользователь перезагрузил VPS сам. Контейнер `deeix-chat-app` остался `Exited (255)`, `restart=no`, поэтому сайт отдавал 502.
- Интерфейс чата показывает оба файла как «Полный текст» (`full_context`). Это значит, что извлечение вернуло текст, и ветка «скан → картинки» (`direct_scan`) для них не сработала. Пользователь утверждает, что в PDF текста нет. Возможные причины: в PDF есть небольшой текстовый слой (штамп ЭП и т. п.) либо включён OCR-резерв для PDF. Не проверено.

## Что было предложено пользователю (выполнение не подтверждено, проверить)
1. Поднять приложение: `docker compose -f docker-compose.sqlite.yml -f /opt/deeix-ru/compose.override.yml up -d` из `/opt/deeix-chat/DEEIX-Chat/deploy`.
2. `docker update --restart unless-stopped deeix-chat-app`, и прописать `restart: unless-stopped` в `/opt/deeix-ru/compose.override.yml` (иначе пропадёт при `--force-recreate`).
3. Лимит памяти контейнера: `docker update --memory 420m --memory-swap 700m deeix-chat-app`, в override: `mem_limit: 420m`, `memswap_limit: 700m` (с 2 ГБ swap можно поднять).
4. Swap-файл `/swapfile`: сначала 1 ГБ, затем пользователь попросил 2 ГБ (команды выданы: swapoff, пересоздание, mkswap, swapon). Запись в `/etc/fstab` и `vm.swappiness=10` в `/etc/sysctl.d/99-swappiness.conf` выданы. Что реально выполнено — проверить `swapon --show`, `free -m`, `tail /etc/fstab`.

## Что ещё не выяснено
- Что именно съело память при обработке/отправке этих двух PDF: штатная обработка оригинала, OCR-резерв, либо код патча. Нужен контролируемый замер: приложение в покое (`docker stats --no-stream`), затем один меньший PDF (доп. соглашение), наблюдение `watch -n 2 'docker stats --no-stream; free -m'`. Только после того как контейнер ограничен по памяти и есть swap. Эти два PDF без защиты не отправлять.
- Включён ли OCR-резерв для PDF и какой движок (админка DEEIX → настройки файлов/OCR; или `grep -i ocr /app/config.yaml` в контейнере).
- Размер извлечённого текста у этих файлов и откуда он взялся.
- Причина перезагрузки не связана ни с чем кроме зависания; проверять журнал `journalctl -b -1 --since "2026-10-15 21:44" --until "2026-10-15 22:00" | grep -v 'UFW BLOCK'`.

## Подозрения по коду патча (проверить в исходниках)
Патч: `patches/scan-pdf.patch` в аддоне (`deeix-ru-addon.tar.gz` в репозитории Dyslexia2813/deeix-ru-build). Новый пакет `backend/internal/infra/extraction/pdfpageimages` на pdfcpu.
- `promoteScanOnlyPDF` (в `extraction/service.go`) вызывается только после ошибки `pdf_no_extractable_text`; читает весь PDF через `api.ReadValidateAndOptimize` (MaxPages 1, но валидация всего файла).
- При отправке (`service_scan_pdf.go`) PDF читается в память целиком (до 64 МБ), затем `pdfpageimages.Extract` с до 30 страниц; в пакете лимиты `maxEmbeddedImageBytes=48 МБ`, `maxDecodedPixels=120 млн` (при декодировании в RGBA это сотни МБ). На сервере с ~300 МБ свободной памяти такие лимиты слишком щедрые. Стоит снизить и не держать все страницы одновременно.
- Но для этих двух файлов ветка `direct_scan` по интерфейсу не включалась, так что патч мог и не участвовать. Не утверждать виновность без замера.

## Состояние патча
- Пакет `pdfpageimages` прошёл свои тесты в изолированной сборке; весь бэкенд локально не компилировался (Go-прокси недоступен в облачной среде), компиляция только на GitHub Actions. Тесты `service_scan_pdf_test.go` написаны, не запускались.
- Патч применяется на чистый тег `v0.4.4-beta.4` вместе с `ru-locale.patch` в любом порядке; `install.sh` поддерживает `--no-scan-pdf`.
