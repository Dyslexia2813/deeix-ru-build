## Как вносятся изменения (русификация)
Русификация сделана как установочный аддон, а не форк, чтобы обновления апстрима можно было ставить поверх.
1. Аддон: `deeix-ru-addon.tar.gz` (исходники `deeix-ru-addon/`). `install.sh [--check|--uninstall] <репо>` применяет `patches/ru-locale.patch` через `git apply` (идемпотентно) и копирует `files/apps/web/.` в `apps/web/`. Правки существующих файлов идут патчем, новые файлы просто копируются. Сейчас патч затрагивает 18 файлов (15 фронтенд, 3 бэкенд).
2. Пользователь загружает архив в deeix-ru-build (важно: закоммитить, один раз архив «не закоммитился» и кнопок не было) и запускает workflow `build-ru.yml` с `tag=v0.4.4-beta.4`.
3. Выкладка на VPS вручную:
   - фронтенд: распаковать новый `out` в `/opt/deeix-ru/out`, затем `up -d --force-recreate`;
   - бэкенд: работающий bind-mount бинарник перезаписать нельзя (`Text file busy`): остановить `app`, скопировать, `chmod +x`, `up -d --force-recreate`;
   - проверка: `healthz`.
4. Откат: вернуть прежние `out` и бинарник (хранить копии) или `install.sh --uninstall` в исходниках и пересобрать.
5. Проверка аддона перед выдачей (на стороне Claude): `pnpm --filter @deeix/web check` в рабочей копии, `git apply --check` и установка/удаление на чистом клоне тега. Go локально не собирается (тулчейн не скачивается), бэкенд проверяется только gofmt и сборкой на GitHub.

### Как DEEIX принимает скиллы и MCP (по исходникам и документации DEEIX)
- Скиллы. Вручную: раздел Skills & Prompts → New (название ≤64, триггер ≤64, описание ≤256, SKILL.md ≤10 000 символов, переключатель Enabled). Через API: `POST /api/v1/admin/skills` — общие, видны всем, нужна роль админа; `POST /api/v1/skills/mine` — личные. Skill — контекст на один ход, команд не выполняет. До 32 скиллов на сообщение; лимит общий с MCP-инструментами («Selectable tools per message»), настраивается до 128.
- MCP. Принимаются только серверы по Streamable HTTP (stdio и SSE в документации не описаны). Админка → Tools: включить «Enable MCP tools», добавить сервер (имя, статус, URL, необязательный токен, заголовки JSON), нажать Sync. Лимиты по умолчанию: 5 запросов к модели, 8 вызовов инструментов, таймаут 10 с, повторов 0. В документации описаны только инструменты (tools); prompts и resources не упомянуты.
- Следствие: pravo-mcp работает только по stdio, значит нужен мост stdio→HTTP (например, `mcp-proxy`).
- Совместимость формата скиллов. Прямо без доработок нет. Шапка YAML вырезается; лимит 10 000 символов превышают 35 из 147 файлов (в contract-law: nda-review ~20,7 тыс., vendor-agreement-review ~16,9 тыс.); триггер нужно собирать из имён pack и skill, иначе есть дубли имён между packs.
- Сверено с исходниками DEEIX v0.4.4-beta.4 (2026-10-15, клон по тегу). Вход: `POST /api/v1/auth/login` {username, password} → `data.accessToken` (заголовок `Authorization: Bearer …`); при 2FA в ответе `twoFactorRequired`, `twoFactorChallengeToken`, `verificationMethods`, затем `POST /api/v1/auth/2fa/verify` {challengeToken, verificationMethod: two_factor|email, code}. Ответы обёрнуты в `{errorMsg, errorCode, data}`, списки — `data: {total, results}`. Скиллы: общие `/api/v1/admin/skills` (роль админа), личные `/api/v1/skills/mine`; GET (список, page_size до 1000), POST, PATCH `/{id}`, DELETE `/{id}`. Поля: `title` ≤64, `trigger` ≤64, `description` ≤256, `markdown` ≤10 000 (лимиты в символах, не байтах), `enabled` (по умолчанию false, при создании нужно слать true), `sortOrder`. Триггер нормализуется (ведущие «/» срезаются) и уникален в своей области: повтор даёт 409 `skill_trigger.already_exists`. Текст markdown хранится как есть: YAML-шапку DEEIX сам не вырезает.
- Как скилл попадает в запрос: все выбранные скиллы одним системным сообщением (`<skill_context>`, у каждого title, trigger, description, content). В «контракте» сказано: скиллы не дают права вызывать инструменты, их можно вызывать только если они явно выбраны и предоставлены платформой для этого разговора. Значит, скилл, который просит обратиться к pravo, сработает только если инструмент pravo выбран в этом сообщении. Каждая часть нарезанного скилла занимает отдельный слот из лимита выбираемых скиллов и инструментов на сообщение.

### pravo-mcp на VPS (сделано 2026-10-14)
- Каталог `/opt/pravo-mcp`: окружение `venv` (Python 3.12.3, нужен был пакет `python3.12-venv` из apt) и `bridge.py`. Клон ru-legal после установки удалён. Установлено из `mcps/pravo` репозитория: `pravo-mcp 0.1.0`, `fastmcp 3.4.8` (ниже 4, как нужно). Баннер «Update available: 4.1.0» игнорировать, `pip install --upgrade fastmcp` не запускать.
- Мост: `bridge.py` — прокси fastmcp stdio→HTTP (отдельный mcp-proxy не нужен). Служба systemd `pravo-bridge` (`/etc/systemd/system/pravo-bridge.service`, DynamicUser, Restart=always, автозапуск) слушает `172.19.0.1:8765`, путь `/mcp`. Это шлюз сети `deeix-chat-network` (подсеть 172.19.0.0/16, контейнер `deeix-chat-app` = 172.19.0.2). Наружу порт не открыт.
- Файрвол: `ufw allow from 172.19.0.0/16 to 172.19.0.1 port 8765 proto tcp`. До этого ufw пропускал только 22/tcp.
- Проверено: из контейнера `deeix-chat-app` мост достижим (ответ 406 на обычный GET — норма); в DEEIX сервер `pravo` добавлен (админка → Tools → MCP, URL `http://172.19.0.1:8765/mcp`, Sync), видны 5 инструментов; вызов `search_npa` из чата работает (модель `deepseek-anthropic`).
- Патч `server.py` (`venv/lib/python3.12/site-packages/pravo_mcp/server.py`). Портал принимает тип документа только как GUID, а исходный код отдавал `doc_type` как есть: `federal_law` и «Федеральный закон» давали HTTP 400, `list_document_types` читал несуществующее поле `code` и показывал пустые коды. Что сделано: `list_document_types` отдаёт GUID в `code` (47 типов); `search_npa` принимает GUID, название типа или алиасы (`federal_law`, `federal_constitutional_law`, `presidential_decree`, `government_resolution`, `order`, `code`); неизвестный тип даёт ошибку со списком допустимых. Патч лежит только внутри окружения и пропадёт при переустановке или обновлении пакета; скрипт патча был одноразовым и не сохранён, при необходимости воспроизводится по этому описанию.
- Ограничение источника: `publication.pravo.gov.ru` — реестр официальных публикаций (примерно с 2011 года). Действующих редакций базовых актов (ГК, закон РФ от 07.02.1992 № 2300-1 и т. п.) в нём нет: поиск находит только законы, вносящие в них изменения. `search_npa` ищет по подстроке в названии, выдача шумная (региональные акты), поэтому фильтровать по типу документа.
- Патч №2 (ИПС, 2026-10-14; скрипт `patch_ips.py` выдан файлом в чате, в репозиторий не положен): `search_npa` и `get_npa` возвращают `eoNumber` (номер публикации); новый инструмент `find_linked_documents(pubnumber)` отдаёт хеши документов, на которые ссылается акт (по ссылкам в его тексте в ИПС); `get_npa_version_at_date(document_hash, on_date, article, offset, max_chars)` переписан на `/legislation/documenttext`: редакция выбирается по дате двоичным поиском по номеру `rdk`, текст отдаётся как plain text, статья отдельно (`article="16"`), есть постраничное чтение. Инструментов теперь 6. Проверено на VPS на законе 2300-1 (хеш `7d78b95f…`): ст. 16 на сегодня — `rdk 54` (от 2026-10-01), на 2020-01-01 — `rdk 29` (от 2019-10-01), на 2005-06-01 — `rdk 7` (от 2004-12-21).
- Как устроен ИПС (по пробам с VPS): `/api/ips/legislation/document` принимает один из `hash`, `nd`, `pubnumber` и отдаёт HTML; `/api/ips/legislation/documenttext?hash=…` отдаёт JSON (`docid`, `doctext` в виде HTML, `rdk`, `baseid`). `pubnumber` равен `eoNumber` из портала публикаций, но даёт сам этот акт, а не изменяемый: хеш изменяемого акта берётся из ссылок в его тексте. Параметр `onDate` ИПС игнорирует; редакции выбираются номером `rdk` (у закона 2300-1 их 57, `rdk=58` даёт 404); без `rdk` отдаётся действующая сейчас редакция. Дата редакции — дата вступления в силу (в заголовке «№ 2300-I от 01.10.2026»); в конце списка есть ещё не вступившие в силу (2027 г.), у части редакций дата одна и та же. Поиска по ИПС (swagger, search) нет.
- Патчи №3–4 (2026-10-15; `patch_fix.py` и `patch_fix2.py`, выданы файлами в чате, в репозиторий не положены): в ответ `get_npa_version_at_date` добавлены `server_date` (сегодня, Москва), `in_force_today`, `current_edition_rdk`, `current_edition_date` (чтобы модель не сомневалась, действует ли редакция); исправлены границы статей: в ИПС индекс статьи записан как `Статья 16<span class="W9">1</span>.`, после патча заголовок читается как `Статья 16¹.`; номер статьи принимается как `16-1` и `16.1`. Проверено на законе 2300-1: ст. 16 сегодня — 9 734 символа (без ст. 16¹), ст. 16¹ — 6 864 символа, ст. 16 на 2020-01-01 (`rdk 29`) — 1 521 символ. Все патчи (№1–5) живут только внутри окружения и пропадут при переустановке пакета.
- Патч №5 (2026-10-15; `patch_fix3.py`, выдан файлом в чате; применение на VPS не подтверждено): в ответ `get_npa_version_at_date` добавлены `edition_label` («редакция № 54 от 01.10.2026»), `edition_status` («действует сейчас» / «не действует сейчас: заменена более поздней редакцией» / «ещё не вступила в силу») и `current_edition_label`; в описание инструмента добавлено указание не показывать пользователю слово rdk. Причина: модель показывала в ответе «rdk 54», пользователю это непонятно. Нужен предварительно патч №3. После применения нажать Sync у `pravo` в DEEIX.

## Нестандартные детали и грабли

### Выкладка и сборка
- Бинарник, смонтированный в контейнер, нельзя перезаписать на лету (`Text file busy`): сначала остановить `app`. После замены `out` тоже использовать `--force-recreate`.
- Цепочка команд с `rm -rf tmp-backend` удалила распакованный файл до копирования; перед копированием перераспаковывать.
- Архив надо именно закоммитить в GitHub; иначе workflow собирает старое.
- Проверка, что фронтенд новый: искать строку «Export PDF» / «Экспорт в PDF» в `out/_next`.
- Backend-изменения требуют новый бинарник, фронтенд-изменения только новый `out`.
- Архитектурные правила репозитория при `pnpm check`: нет необъяснённых приведений типов (`as`), shared не зависит от entities/features, entities не зависят от features.
- Автоназвание: ручное «Переименовать» работало всегда, ломалась только автозамена на первом ответе.

### Скиллы и MCP
- Лимиты DEEIX считаются в символах: название 64, триггер 64, описание 256, SKILL.md 10 000.
- Разбитые скиллы нужно подключать вместе: у `contract-law-nda-review` три части (`-1`, `-2`, `-3`), в каждой есть напоминание об остальных. Последняя часть почти целиком раздел Attribution.
- Тексты скиллов ссылаются на то, чего в DEEIX нет: `/contract-law:review`, `~/.ru-legal/profiles/contract-law/PROFILE.md`, вызовы вида `pravo.search_npa(...)`. Названия инструментов после Sync в DEEIX могут отличаться, не проверено.
- Содержание ru-legal сырое: issue #2 / PR #3 — в nda-review и vendor-agreement-review непроверенные номера судебных дел и статистика без источника; PR #3 их убирает, но в исходном репозитории не влит. PR #10 построен поверх #3 и чинит склеенные кириллица-латиница токены (затронуты 7 из 10 импортируемых скиллов); в импорт берётся коммит `1723bf3` (оба PR). В nda-review после PR осталась ссылка «по данным RTM Group за 2018–2020 годы» как источник качественного утверждения о причинах отказов истцам; источник не проверялся. До проверки юристом эти материалы как справочные использовать нельзя. Файл констант `references/constants/2026.yaml` устарел (МРОТ, НДФЛ, госпошлины); PR #1 про налоговые изменения не влит.
- pravo-mcp ходит на pravo.gov.ru по обычному HTTP: TLS на портале сломан с 2026-05-21, клиенты с автоматическим переходом на https получают таймаут. Когда портал починят, адреса нужно вернуть на https.
- Для `ips.pravo.gov.ru` в код зашит публичный Basic-пароль из фронтенда портала (помечен как возможный к ротации; значение здесь не записано). Если сменится, перестанут работать `get_npa_version_at_date` и `find_linked_documents`.
- API портала официально не документирован: структура ответов восстановлена сообществом, возможны сбои при его изменениях.
- `fastmcp` должен быть версии ниже 4: обычная установка pip подтянула 4.1.0, пришлось ставить `fastmcp>=3.2,<4`.
- Покрываются только федеральные НПА; тексты больших кодексов могут приходить ссылкой на PDF/XML, а не inline.
- Рабочая сессия Claude не видит внешние сайты, кроме реестров пакетов и GitHub, поэтому проверку pravo-mcp на живом портале нужно делать на VPS или своей машине.
- Вход скрипта по паролю: пароль вводится по запросу (или в переменной `DEEIX_PASSWORD`), при 2FA скрипт запросит код. Вход ограничен по частоте запросов: не запускать в цикле.
- `enabled` в DEEIX по умолчанию false: скилл, созданный без `enabled: true`, не виден в меню «/». Импортёр всегда шлёт true.
- Скиллы из ru-legal рассчитаны на Claude Code: многие ссылаются на файл профиля на диске (`~/.ru-legal/profiles/…/PROFILE.md`) и на команды вида `/contract-law:review`; в DEEIX их нет, модель должна спрашивать данные у пользователя (пометка в первой части это требует). Относительные ссылки на файлы рядом со скиллом не работают.
- Мост привязан к `172.19.0.1`. Если сеть `deeix-chat-network` пересоздать целиком (например, `docker compose down`), её адрес может измениться: тогда поправить `BRIDGE_HOST` в `/etc/systemd/system/pravo-bridge.service`, правило ufw и URL в DEEIX. `up -d --force-recreate` сеть не трогает.
- Длинные вставки в веб-терминал 1Panel искажаются (строки склеиваются в эхо, хотя команды обычно выполняются верно). Длинные скрипты лучше отдавать файлом через раздел «Файлы» 1Panel, запускать и сразу удалять.
- `apt install` один раз упал с «dpkg was interrupted»: лечится `dpkg --configure -a`, перед этим убедиться, что apt/dpkg никто не использует.
