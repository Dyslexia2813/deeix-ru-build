# Углублённая проверка по типу договора

Проверка входящего договора по внутренним правилам (позиции) компании: определяет тип договора по заголовкам и приложениям, выбирает профильный скилл и сводит результат в одно заключение. Основано на commercial-legal/review от Anthropic (Apache 2.0), адаптировано под российскую классификацию договоров.

Каждый профильный скилл глубже работает со своим видом договора: поставка ИТ-оборудования и облачная подписка на 3 года имеют принципиально разные риски.
- **NDA (соглашение о неразглашении)** → /договор-nda-проверка (сортировка 🟢 приемлемо / 🟡 обсудить / 🔴 критично).
- **Услуги / поставка / подряд** → /договор-услуги-поставка-проверка (полная проверка, мы покупатель).
- **SaaS (программа как облачная услуга) / подписки** → /договор-saas-проверка (надстройка над проверкой услуг: автопролонгация, повышение цены, уровень сервиса (SLA), субподрядчики по обработке данных).
- **Договоры с госкорпорациями / по 44-ФЗ и 223-ФЗ** → проверка тендерного договора (отдельный скилл другого пака, сейчас не установлен).

Профильные скиллы доступны, только если пользователь выбрал их в этом же сообщении. Если нужный выбран — следуй ему полностью (для скиллов из двух частей — обе части). Если нет — предложи выбрать его в меню «/», а пока проведи проверку по /договор-проверка, если он выбран, иначе — по общим принципам ГК РФ, явно отметив, что профильная методика не применялась.

## Перед началом уточни у пользователя (если не сказано в сообщении)
- Наша сторона и позиция компании (внутренние правила): мы покупатель / мы продавец; ключевые требования и неприемлемое условие.
- Кто и до какой суммы согласовывает (порядок эскалации).
- Подтверждать ли выбор типа договора перед анализом (по умолчанию — да).

Без ответов — работай с разумными допущениями и перечисли их в начале заключения.

Если выбран инструмент **pravo** — сверяй текст и редакцию статей (search_npa); если нет — предупреди, что нормы приведены без сверки с актуальной редакцией.

## Порядок работы

### Шаг 1. Получить договор
Файл или текст в чате. Если ничего нет — попроси приложить договор (.docx, .txt, .md, .pdf; PDF только с текстовым слоем — скан без распознавания не подойдёт).

### Шаг 2. Сначала структура — заголовки
До чтения тела выпиши:
- главное название («Договор оказания услуг», «Договор поставки товаров», «Соглашение о неразглашении», «Лицензионный договор»);
- все приложения, допсоглашения, спецификации, протоколы («Приложение №1 — Спецификация», «Приложение №2 — Регламент SLA», «Приложение №3 — ДОУ (договор об обработке ПДн)»).

Это и есть основной признак типа. Не опирайся только на слова в тексте: 40-страничный договор услуг со словом «конфиденциальность» повсюду — **не NDA**.

### Шаг 3. Выбрать профильный скилл по структуре
| Заголовок договора / приложения | Скилл |
|---|---|
| «Соглашение о неразглашении», «NDA», «Договор о конфиденциальности» (как **основной**) | /договор-nda-проверка |
| «Договор оказания услуг» (гл. 39 ГК), «Договор подряда» (гл. 37 ГК), «Договор на выполнение работ» | /договор-услуги-поставка-проверка |
| «Договор поставки» (§3 гл. 30 ГК, ст. 506–524), «Договор купли-продажи» (гл. 30 ГК) | /договор-услуги-поставка-проверка (с учётом специфики поставки) |
| «Подписка», «SaaS», «Облачные услуги», услуги с ежемесячной/ежегодной оплатой и автопролонгацией, лицензия на ПО с периодическими платежами | /договор-saas-проверка (надстройка над проверкой услуг) |
| «ДОУ», «Договор об обработке персональных данных», «Поручение на обработку ПДн» (приложение или отдельный) | пометка для /договор-услуги-поставка-проверка → раздел 152-ФЗ |
| «Регламент SLA», «Соглашение об уровне сервиса» (приложение) | пометка для /договор-saas-проверка → раздел SLA |
| «Лицензионный договор» (ст. 1235, ст. 1286 ГК) на ИС, патенты, товарные знаки | /договор-услуги-поставка-проверка (с учётом специфики ИС) |
| «Договор аренды» (гл. 34 ГК) | /договор-услуги-поставка-проверка (с учётом специфики аренды) |
| «Договор займа» (гл. 42 ГК), «Кредитный договор» (гл. 42 §2) | не покрывается — нужен отдельный скилл |

Часто применяется несколько скиллов:
- услуги + ДОУ в приложении → проверка услуг с пометкой о поручении на обработку ПДн;
- SaaS-подписка + спецификация + SLA → /договор-saas-проверка (покрывает все три);
- услуги + спецификация с автопролонгацией → проверка услуг + надстройка SaaS.

Если по заголовкам тип действительно неясен (например, просто «Соглашение» без приложений) — прочитай первые 2 страницы текста, определи и остановись на выборе.

### Шаг 4. Подтвердить выбор (по умолчанию включено)
Если пользователь не отказался от подтверждения, покажи:
```
Планирую проверку как: [тип(ы) договора].
Документы:
- [название основного договора] → [скилл]
- [Приложение А] → [как будет обработано]
- [Приложение Б] → [как будет обработано]
Всё верно? (да / нет — или подскажите, что не так)
```
Жди подтверждения; если пользователь поправил — примени и продолжай. Если подтверждение отключено — продолжай сразу, но запиши выбор в начале заключения.

### Шаг 5. Провести проверку
Следуй каждому профильному скиллу полностью. Если их несколько — последовательно, затем **сведи всё в одно заключение**; отдельных заключений по каждому скиллу не делай.

### Шаг 6. Эскалация
Если какой-то вопрос выходит за полномочия проверяющего по порядку согласования: если пользователь выбрал /договор-эскалация — подготовь по нему, кому передать и запрос; если нет, предложи выбрать его в меню «/».

### Шаг 7. Предложи дальнейшие шаги
- /договор-резюме-для-руководства — двухминутное «можно ли подписывать» для руководства;
- предлагаемые правки в режиме исправлений Word — внешними средствами (здесь .docx не создаётся);
- /договор-сроки-и-продление — если найдена автопролонгация;
- /договор-допсоглашения — если есть допсоглашения.
Для каждого: если не выбран — предложи выбрать в меню «/».

## Результат
Полное заключение в формате профильного скилла: в начале — выбранный тип и допущения; далее отклонение за отклонением, конкретные предлагаемые правки, названный согласующий.

## Особенности российских договоров
1. **Услуги или подряд** (гл. 39 и гл. 37 ГК) — нормы существенно разные. Услуги: результат — действия (ст. 779 ГК), детальных требований к результату нет, заказчик платит за процесс. Подряд: результат — материальный или нематериальный продукт (ст. 702 ГК), есть ответственность за качество. Если документ назван «услуги», а описывает создание продукта (например, ИТ-разработку), отметь: «формально услуги, по содержанию ближе к подряду».
2. **Смешанные договоры** (ст. 421 п. 3 ГК) — например, «поставка оборудования с установкой и обслуживанием». Может понадобиться несколько скиллов: проверка поставки + проверка услуг + SaaS (если есть периодическое обслуживание).
3. **Госкорпорации (44-ФЗ / 223-ФЗ)** — обязательные типовые формы, полномочия проверяющего ограничены, ключевые условия менять нельзя. Отметь и направь к скиллу проверки тендерного договора (другой пак, сейчас не установлен).
4. **Договор в иностранной валюте** — автоматическая пометка: валютный контроль (173-ФЗ), автоматическая эскалация (/договор-эскалация).

**Применимое право не РФ** (английское, кипрское и т. д.) — автоматическая эскалация юристу с международной практикой: из-за текущих ограничений на признание иностранных судебных решений в РФ такие договоры проблемны к исполнению. Скилл сам этот вопрос не решает.

> Предварительный выбор типа и анализ ИИ для использования квалифицированным юристом; не юридическая услуга (ст. 2 ФЗ-63 «Об адвокатской деятельности») и не замена консультации юриста/адвоката. ИИ может ошибаться и приводить устаревшие нормы. Выбор типа для критичных договоров (M&A — слияния и поглощения, инвестиционные сделки, госконтракты) проверяет юрист; существенные решения — только с профильным адвокатом. Авторы ru-legal не отвечают за решения на основе результатов; использование — на свой риск.
